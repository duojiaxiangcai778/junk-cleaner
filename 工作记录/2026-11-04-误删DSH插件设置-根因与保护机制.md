## 三、根因

**根因 = `junk_items.py` 里 `id="pnpm_store"` 被标成 `level="safe"`（默认勾选），
路径是 pnpm 的全局包存储。**

链条：
1. ai 清理工具 11-03 17:02 把 pnpm store 清空（2.2 GB）；
2. DSH 的插件依赖全部由 pnpm 装在 `profiles\.generations\live\<pkg>+<ver>+<hash>\node_modules`，
   依赖 store 里的数据；
3. store 没了 → pnpm 下次校验判定 node_modules 无效 → 清空重建 → 无网络/无 store 时装不上；
4. 11-04 14:04 DSH 启动读 generation 的 `package.json` 失败 → 进 Safe Mode → **所有插件被禁用**，
   用户看到的「插件设置全丢失」就是这个。

放大因素：
- `updater_residue` 用 `%LOCALAPPDATA%\*-updater` 通配，顺带吃了 `dsh-desktop-updater`；
- `dsh_cache` 直接写死 `%APPDATA%\dsh-desktop\Cache`，DSH 运行中删它的 Cache 会失败并扰动界面。

**另一个必须说清的技术事实**：pnpm store 里的包和 node_modules 是**同一份磁盘数据的两份名字（硬链接）**。
删 store 释放的「2.2 GB」是虚的 —— 除非连 node_modules 一起删，否则磁盘几乎不回收。
也就是说这一项**收益接近 0、风险极高**，v2.2.0 把它当「可清理」是设计错误，不是用户点错。

## 七、教训 / 下次注意

1. 「删了能省多少空间」不能按文件大小累加算，**硬链接、符号链接、压缩存储会虚报**。
   判断一个目录值不值得清，先问「它是不是某人在用的数据」。
2. 任何 `AppData` 下**不带 Cache/Code Cache/Temp 字样**的目录，默认视为配置/数据，宁可不清。
3. 通配符（`*-updater` 这类）必须配黑名单，不能只靠「看起来像垃圾」。
4. 「可清理」项一旦出问题就是不可逆的（本工具全程 `os.remove`，不进回收站）。
   所以保护必须做在**删除动作那一层**（guard），不能只做在清单配置层（junk_items）。
