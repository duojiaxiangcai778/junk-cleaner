## 二、删除慢（用户反馈①）

### 排查

一开始怀疑是 UI 回调太频繁（每删一个文件往 Tk 事件队列塞一个 lambda），
读了 `cleaner._rm_tree` 后确认**没有** progress 调用，不是这个原因。
真正的三处浪费：

1. **逐文件调 guard**：`_rm_tree` 对每个文件跑一次 `guard.is_protected(fp)`，
   里面又 `os.path.abspath()` 一次。清 2 万个小文件 = 2 万次无谓的路径规范化 +
   字符串匹配。而入口已经 `is_protected_root` 判过整棵树了。
2. **`_empty_dir` 每个子目录 → `_rm_tree` → `is_protected_root`**：
   `is_protected_root` 要查 `.git` / `package.json` / `node_modules` /
   `manifest.json` / `pyproject.toml` **5 次 `os.path.exists`**。
   Temp 下几千个子目录 = 上万次 stat，全在同步 IO 上。
3. **`th.join(UNLOCK_TIMEOUT=90)`**：失败文件走解除占用时最多阻塞 90 秒。
   这个有超时保护，属于兜底，不动。

### 顺带发现的**安全漏洞**（比慢更要紧）

旧 `_rm_tree` 用 `os.walk(topdown=False)`（自底向上）。这意味着它**先钻进子目录把文件删光**，
等回头处理到 `node_modules` / `.dsh` 这一层目录本身时，才发现它该受保护 ——
**里面的东西早就没了，保护晚了一步，等于没保护。**

### 改动（`src/cleaner.py`）

`_rm_tree(path, fails=None, progress=None, check_root=True)` 重写：

- 改 `topdown=True`，在 `dirs[:]` 里过滤掉受保护目录和 junction，**直接不下钻**
- 逐文件不再调 guard（父目录已经判过）
- 目录级判断用 `guard.is_protected`（纯字符串，零 stat），不再用 `is_protected_root`
- 记录 `all_dirs`，最后**逆序 rmdir** 收空目录（一趟遍历，不额外 walk 第二遍）
- `progress` 每 500 个文件回调一次，界面能看到「已处理 N 个文件」在动
- `check_root=False` 参数：入口已判过时不再重复 5 次 exists

`_empty_dir(path, fails=None, progress=None)`：
子目录交给 `_rm_tree` 时带 `check_root=False`（第 139 行已用纯字符串判过名字）。
`_clean_item_inner` 把 `progress` 透传下去。

### 验证

| 验证 | 结果 |
|---|---|
| 2 万个小文件压测（200 目录 × 100 文件） | **6.61 秒，3026 个/秒**；造文件本身花了 7.44 秒，说明已经是 SSD 的 IO 极限，不是代码拖累 |
| 安全回归：`sub\node_modules\pkg\index.js` + 同级 `junk.txt` | `freed=10 failed=0 skipped=1`；**node_modules 里的文件保住了**，普通垃圾照删 |
| 回归 `selftest_guard.py` | 66 通过 / 0 失败 |

## 三、右下角按钮「灰色」（用户反馈②）

### 排查过程（走了点弯路，记下来）

1. 先看 `FlatButton.set_enabled`：禁用态 `fg=#9fc4ee`、`bg=#4a9eff`（亮蓝底 + 浅蓝字），
   对比度低，确实像「字灰了」。
2. 又怀疑布局把底部挤出去了 —— 因为截图里**完全看不到底部栏**。
3. 用 `winfo_*` 打印控件几何做定论：

```
Frame(客户区)   y=14  h=750
Treeview        y=173 h=416
detail          y=612 h=50
hint            y=672 h=23
foot            y=716 h=34     ← 底部栏一直是存在的
  Button「清理选中项」 h=34 w=91
```

**布局本身没问题**，底部栏确实在客户区底部（716+34=750 贴底）。
截图看不到是因为窗口被移到副屏时被 `SetWindowPos` 拉成 1536×864，
加上 125%/150% DPI 缩放，物理高度超出屏幕，底部被挤到屏幕外。

### 改动（`src/main.py`）

**A. 窗口尺寸自适应**：不再写死 `1180x780`，改成按屏幕可用区域收
（宽 ≤ 88%、高 ≤ 86%），并居中偏上。这样在小屏 / 高缩放下底部按钮永远在屏幕里。

**B. pack 顺序修正**（保险）：原来 `wrap` 用 `expand=True` 且在详情区/底部栏之前 pack，
理论上会被挤压。改成底部区块 `side="bottom"` 先占位，`wrap` 最后 pack 吃中间剩余：

```
foot → line_foot → hint → detail → line_detail   （side="bottom"，从下往上）
wrap.pack(fill="both", expand=True)              （最后）
```

**C. 按钮颜色重做**：禁用态改成「压暗的底 + 提亮的字」，和可点状态一眼分清：

| 状态 | 背景 | 文字 |
|---|---|---|
| 可点（primary） | `#4a9eff` 亮蓝 | `#ffffff` 纯白 |
| 禁用（primary） | `#2b5f9c` 暗蓝 | `#d6e9ff` 亮蓝白 |
| 可点（danger） | `#d9534f` | `#ffffff` |
| 禁用（danger） | `#8c3a3a` 暗红 | `#d6e9ff` |

hover 也加了 `self._on` 判断 —— 禁用时不再跟着鼠标变色（以前禁用态还在 hover 变亮，看着像能点）。

## 七、教训

1. **保护做得越"全"越容易把功能做死。** QQ/微信那次是我自己想当然了 ——
   用户要删的东西不该被我"体贴"地保护起来。保护的对象必须是**用户明确说不能动的**，
   不是"看起来重要"的。
2. **`os.walk(topdown=False)` 做删除过滤是危险的**：它天然是先删子再判父，
   任何"父目录级"的保护都会晚一步。要过滤就必须 `topdown=True` 且改 `dirs[:]`。
3. **界面看不到某个控件，先量坐标再改代码。** 这次差点盲目重排布局 ——
   实际布局是对的，问题在窗口尺寸。`winfo_rooty()` 一把就能定论，比截图靠谱
   （窗口会被遮挡、DPI 会缩放、副屏截图还会抓到别的窗口）。
4. **PowerShell 写 Python 脚本传中文路径要用 `-Encoding utf8`**。
   `-Encoding ascii` 会把 `E:\垃圾清理工具` 里的中文变成 `?`，
   Python 报 `OSError: Invalid argument`，看着像路径不存在，实际是编码丢了。
5. **PyInstaller 的 `--add-data` / `--icon` 相对路径是相对 `--specpath` 的**。
   `--specpath build` 时写 `src\icon.ico` 会被解析成 `build\src\icon.ico`，
   直接 `ERROR: Unable to find`。要用绝对路径。
